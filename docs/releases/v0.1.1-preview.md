# regiondb v0.1.1-preview

`v0.1.1-preview` is an evaluation release for the current durability and
cross-platform packaging behavior. It is not production-ready and does not
make stable wire, on-disk, CLI, or Go API compatibility commitments.

## Highlights since v0.1.1-alpha

- The data-directory process model now provides portable single-writer
  ownership and explicit read-only access while retaining bounded in-process
  chunk caching.
- Real TCP and TLS integration suites, native Windows coverage, repeated
  stress checks, structured lifecycle logging, and runtime counters expand the
  operational evidence.
- WAL group commit provides an explicit throughput/durability trade-off, while
  crash boundaries cover synchronized atomic replacement, WAL replay, and
  checkpoint truncation.
- The opt-in `fs_region_v1` experiment includes correctness and benchmark
  evidence, but the published comparison retains `fs_split_v1` as the default.
- GoReleaser produces Linux, macOS, and Windows archives for AMD64 and ARM64,
  SHA-256 checksums, and one SBOM per archive.

## Durability contract

All durability modes append a complete, checksummed record to the write-ahead
log before replacing the chunk file and updating the in-memory cache. A
successful write response means:

- `relaxed`: the WAL append and atomic chunk replacement completed without a
  file or directory sync;
- `fsync-wal` with `-wal-group-commit-updates=1`: the WAL record reached a
  successful file sync before the chunk replacement and acknowledgement;
- `fsync-wal` with `-wal-group-commit-updates=N`, where `N > 1`: the append and
  chunk replacement completed, but up to `N-1` acknowledged records can remain
  beyond the last successful WAL sync. The pending tail is synced on the Nth
  update or orderly close;
- `fsync-checkpoint`: the temporary chunk file was synced before replacement,
  and the replacement's directory entry reached the platform's documented
  commit boundary before acknowledgement.

Before the first WAL record is appended, a new WAL is created through the
synchronized replacement path. Unix commits its parent directory entry with a
directory sync; Windows uses a write-through replacement. A crash after the
first record sync but before chunk replacement is recovered from that WAL in
the same way as any later synchronized record.

At a durable checkpoint, every WAL record is replayed through synchronized
chunk replacement before the WAL is truncated and synced. A failure is
reported at the boundary where it occurs; startup recovery re-evaluates the
resulting WAL and chunk files. On Unix, successful synchronized replacement
requires syncing the parent directory. On Windows, replacement uses
write-through semantics. If neither a directory sync nor a write-through
replacement can commit the new entry, the write fails closed with an
unsupported-durability error. Other sync failures remain write errors.

At startup, recovery replays complete valid WAL records. A final partial record
is discarded. Invalid metadata, a checksum mismatch in a complete record, or a
record that crosses configured geometry bounds fails startup closed. Recovery
does not repair corrupted chunk files or complete corrupted WAL records.

These guarantees end at successful operating-system file and directory sync
calls. Storage hardware, filesystem mount options, virtualization, and the
operating system can provide weaker persistence. The server does not claim
protection against lost writes, write reordering, or corrupted storage below
that boundary.

## Archive contents and verification

GoReleaser builds static `regiondb` binaries for Linux, macOS, and Windows on
AMD64 and ARM64. Linux and macOS use `.tar.gz`; Windows uses `.zip`. Each
archive includes the binary, README, changelog, license, protocol, storage,
concurrency, and Windows documentation.

The release artifacts include a Syft-generated JSON SBOM for each archive and
one `SHA256SUMS` manifest for the published archives. Verify a downloaded
archive from the directory containing `SHA256SUMS`:

```sh
sha256sum -c SHA256SUMS
```

On macOS, use `shasum -a 256 -c SHA256SUMS`.

## Preview checklist

Before publishing the preview:

1. Run `scripts/test/quick.sh` and `scripts/test/full.sh` from a clean tagged
   revision.
2. Repeat the real server integration suite and confirm the stress and crash
   suites complete without flakes.
3. Confirm the durability crash matrix is green on Linux, macOS, and Windows.
4. Run `goreleaser release --clean` with the pinned release environment.
5. Confirm six archives exist: Linux, macOS, and Windows for AMD64 and ARM64.
6. Confirm every archive contains the binary and the documented support files.
7. Confirm every archive has a corresponding SBOM.
8. Verify every line in `SHA256SUMS` against the generated artifacts.
9. Extract each archive and run `regiondb -version` (or
   `regiondb.exe -version`) on its target operating system.
10. Confirm the version output matches the tag and the working tree is clean.

## Upgrade and rollback

The preview does not change the wire protocol, WAL or chunk encoding, CLI
flags, or Go API. The first-create change strengthens when a new WAL directory
entry is committed; it does not require data migration.

Do not rely on a preview data directory remaining readable by a later release.
Stop the server before copying data. To roll back an evaluation, restore a
complete backup created by the same version and geometry, or start with an
empty directory.

## Explicitly out of scope

- Creating or publishing a tag or GitHub Release.
- Stable compatibility or production-readiness guarantees.
- Artifact signing, provenance attestations, installers, packages, or
  container publication.
- Automated data migration or repair.
