# regiondb v0.1.0-alpha

`v0.1.0-alpha` is the first engineering alpha of regiondb. It is suitable for
evaluating the implemented chunk paths and their current durability modes, not
for production data or compatibility-sensitive deployments.

## Included

- Configurable regular- and large-chunk geometry with packed block values from
  1 to 64 bits.
- The checksummed `fs_split_v1` file layout, delta WAL replay, checkpoint
  thresholds, and `relaxed`, `fsync-wal`, and `fsync-checkpoint` durability
  modes.
- Authenticated text commands for block and regular-chunk reads and writes over
  plaintext TCP or TLS 1.2 and later.
- A bounded in-memory LRU chunk cache, a single-writer data-directory lock, a
  fixed connection worker pool, a bounded accepted-connection queue, and
  bounded command lines.
- Seeded direct-storage and TCP scenarios for read, write, and mixed workloads,
  with machine-readable latency and operation counts.

The exact current contracts are described in the
[protocol](../PROTOCOL.md), [storage](../STORAGE_FORMAT.md), and
[concurrency](../CONCURRENCY.md) specifications.

## Explicitly out of scope

- Stable compatibility guarantees for the wire protocol, on-disk data,
  command-line interface, or Go API.
- Production-readiness, migration tooling, replication, multi-process readers,
  transactions, snapshots, or cross-command ordering.
- A portable writer lock: this alpha starts only on Unix platforms that provide
  `flock`.
- Prebuilt cross-platform archives, checksums, an SBOM, or container images.

Do not rely on an alpha data directory remaining readable by a later release.
Back up or discard evaluation data before upgrading.

## Known limitations

- The server requires one shared authentication token and does not provide
  per-user authorization.
- Plaintext TCP exposes the token and data to the network. Use TLS for
  untrusted networks and manage certificates outside regiondb.
- One process owns a data directory for writing. A second process is rejected,
  and there is no read-only process role.
- An absent chunk is distinguishable through chunk reads, but block reads
  return zero for absent data and `EXISTS` reports whether the current block
  value is nonzero.
- Durability guarantees are limited to the documented filesystem calls.
  Hardware, filesystem, and operating-system behavior may provide weaker
  persistence.
- Recovery validates complete WAL records and discards a final partial record;
  corruption in a complete record fails startup closed and has no automated
  repair path.

## Recovery validation

The automated durability suite exercises interrupted WAL appends inside both
the record header and final checksum, repeated ordered replay of replacement
records, and four consecutive 257-record WAL growth, checkpoint, and reopen
cycles. It verifies that complete records survive recovery, incomplete records
do not create chunks, replay preserves the last replacement, each checkpoint
clears the WAL at its configured boundary, and the latest chunk remains
readable after every reopen.

These scenarios validate the documented store behavior on the test host. They
do not extend the filesystem and hardware limitations described above.

## Benchmark caveats

The included scenario programs are diagnostic tools, not performance
guarantees. Results depend on geometry, durability mode, cache state,
filesystem, hardware, operating system, server settings, and whether TLS is
used. Direct scenarios measure an in-process store call; TCP scenarios measure
client encoding and a complete request/response round trip against an existing
plaintext server. Working-set preparation is excluded from the timed loop.

Quick benchmark tests verify completion and JSON structure only. There are no
throughput or latency thresholds, no reference-machine baseline, and no basis
for comparison with general-purpose databases. Record all inputs and the
machine configuration when sharing results.

## Upgrade and rollback

There is no supported migration path into or out of this alpha. Stop the
server before copying a data directory. To roll back an evaluation, restore a
complete backup created by the same version and geometry, or start with an
empty directory.
